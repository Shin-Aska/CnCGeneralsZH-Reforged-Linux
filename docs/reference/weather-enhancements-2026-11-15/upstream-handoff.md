# Optional weather: local upstream preparation

The weather source is committed locally on `main` as `0529ecef` (audio), `e12ff8b8` (weather) and `f91069a2` (haze/lighting). No push or public pull request has been made. Existing upstream history in [`../../upstream-status.md`](../../upstream-status.md) is retained. The protected campaign handoff is unchanged.

The problem addressed is continuous added rain and uniform weather motion, plus low blowing dust and weather haze that could cover water. The proposed behavior is optional gusting weather, intermittent enhanced rain with long dry breaks, layered snow, dry-ground dust, surface rain contacts and coupled ambient/atmospheric presentation. A map's authored precipitation retains its existing behavior. The Weather preference and default-off/Classic/provider gates remain.

The change is client presentation only. It reads copied render terrain/water geometry, uses a bounded private weather clock and deterministic arithmetic, and never writes gameplay wind, world lights or simulation random state. A wet/dry rain transition preserves tree phase and cached random factors while restoring the script's original sway period. Water rings follow the authored rendered polygon/river rest plane; coupling to instantaneous FFT displacement is outside this change.

Weather haze is explicitly composed before actual water, independently of AO, while ordinary warm haze and the horizon remain at their original later phase. Rain transitions use complementary weather/warm weights with one existing shader and separate completion/ownership checks. Both native and Windows dispatch paths are included. Windows compilation/runtime still needs a host with the Windows SDK and game toolchain before an upstream offer; a Linux source audit is not Windows execution evidence.

Ambient rain and wind reuse licensed retail samples through level-specific event clones and owned handles. The normal ambient/master/device/focus path applies. Authored 2D or positional emitters and existing map ambience beds take precedence over an added loop. Pausing blocks new/retried admission; gain modulation does not restart an established loop or modify another event using the same source sample.

The dependency base is this fork's renderer/environment integration, including its native capability routing and render snapshot ownership. This is not a standalone cherry-pick onto an unverified upstream checkout. A maintainer would need to adapt those boundaries to the target revision, preserve backend capability checks and avoid exposing private qualification probes as production flags.

The [weather guide](README.md) records measured-v4 artifact identities, qualification status and implementation limits. The measurement package includes all three matched baseline/final/on-off repeats for each kind (27 runs, 253,800 raw present intervals), phase occupancy and active/fade/dry costs. Active presentation increases the median about 0.3 ms, mean about 0.4 ms and p95 about 0.9–1.0 ms on the controlled scene; rain fades include the extra composition pass. Exact-final scope and unobservable/unrun boundaries are recorded in the linked matrix. It retains outliers and separates actual final screenshots/audio/debugger qualification from timing. A full-cycle average must not conceal active-storm cost. The [randomized startup follow-up](../weather-rain-startup-2026-11-15/README.md) records its separate build and checks; the 27-run timings do not measure that later executable. No unmeasured FPS or hardware GPU-time improvement is claimed.

Before offering upstream, review the final patch against the target revision, reproduce on a Windows host, inspect ordinary gameplay beyond the controlled fixture and attach the exact final evidence. This handoff does not claim upstream runtime validation or acceptance.
